# Ruina Coop

《废墟图书馆》合作联机 Mod，按[设计方案](docs/联机Mod设计方案.md)分阶段开发。Steam房间、房主进度镜像、角色认领、原版卡组/普通核心书/被动编辑均已获用户基本流程双端确认。v16接待跳转、锁定角色、对应配装和准备就绪也已确认。本轮v18修复4A首幕初始化原型的敌方卡组预检，按[后续实施方案](docs/核心书页接待与合作战斗实施方案.md)逐步推进；尚未开放可玩合作战斗。

暂停开发时的版本、已完成内容、未完成目标和运行测试步骤见[当前状态与接续指南](docs/当前状态与接续指南.md)。

## 本地构建

要求 Windows、.NET SDK、.NET Framework 4.6 引用程序集，以及 Steam 版《废墟图书馆》。执行：

```powershell
pwsh -File scripts/pack.ps1 -GameDir 'D:\game\steamapps\common\Library Of Ruina'
```

生成物位于 `dist/RuinaCoop`。游戏程序集只作为本地编译引用，不会复制到包里或提交到 Git。Harmony 使用 NuGet 的 `HarmonyX` 2.9.0。打包时只有 `RuinaCoop.dll` 放在游戏扫描的 `Assemblies` 目录；HarmonyX 及 MonoMod DLL 放在 `Dependencies`，由入口按需加载，以免游戏将依赖重复加载并弹出错误。

关闭游戏后执行 `pwsh -File scripts/install-local.ps1` 安装测试包；脚本会先把旧包备份到忽略目录 `artifacts/install-backups`。也可以手动将整个 `dist/RuinaCoop` 文件夹放入游戏的 `LibraryOfRuina_Data/Mods`，再通过 Steam 的 **LOR With Mods** 启动游戏，并在 Mod 列表中勾选 **Ruina Coop (Development)**。该启动选项使用 `-mod` 参数；见 [SteamDB 的游戏配置](https://steamdb.info/app/1256670/config/)。初次加载时应在 `%USERPROFILE%\\AppData\\LocalLow\\Project Moon\\LibraryOfRuina\\Player.log` 中看到 `[RuinaCoop] Stage 0 bootstrap loaded` 和 `[RuinaCoop] Harmony game-loop probe reached`。未验证的游戏程序集版本会拒绝打补丁并记录 SHA-256。

Mod 不修改原版程序集。卡组、核心书页和被动编辑只改动房主真实游戏模型，房主仍可由原版正常保存；客人会话期间禁止本地存档写入。房主数据仅进入独立的原版 UI 显示对象，不覆盖客端存档模型。初版范围已定为原版游戏加本 Mod，客人不会获得永久关卡解锁。
## 阶段 1 房间测试

在主菜单按 **F9** 打开房间面板。Steam 状态应为 `ready`。房主点击 `Create public room (max 5)` 或 `Create friends-only room (max 5)`，通过面板中的 Room ID 或 `Invite Steam friends` 邀请客人。客人可以输入房间 ID、搜索公开房间，或接受 Steam 邀请。双方都能查看成员列表并离开房间。房主离开时，客人自动退出房间。

以上是房间功能的测试步骤，不应据此开始联机接待。双账号核心流程已验证，最多五人容量等专项仍待验收，见 [阶段 1 验证记录](docs/阶段1验证.md)。
## 阶段 2 进度原型

房主需先通过“继续游戏”载入图书馆存档。开房后，F9 右侧显示房主章节、可用原版关卡、楼层与馆员。客人加入后经 Steam Relay 接收相同的只读快照；房主可以在该面板选择一个“下一关计划”，选择尚未触发原版接待。旧的阶段 1 测试包协议不兼容，双端必须使用相同的阶段 2 测试包。详见 [阶段 2 验证记录](docs/阶段2验证.md)。 单账号自检的命令和 F9 操作见 [本地双端测试方案](docs/本地双端测试.md)。 发给第二位玩家的安装和双人操作步骤见 [给测试玩家的双人测试说明](docs/给测试玩家的双人测试说明.txt)。

## 阶段 3 角色认领原型

房主在 F9 的 **Host progress** 页选关，再到 **Role claims** 页选楼层。玩家可认领或释放该楼层馆员，归属由房主通过 Steam Relay 裁定并同步。v7 已验证的记录见 [阶段 3 认领验证](docs/阶段3认领验证.md)。

## 阶段 3 卡组测试版（v8）

认领馆员后，在 **Deck editor** 添加或移除普通战斗书页。房主检查权限、库存与修订号，再执行原版装备规则并同步结果；原版改卡入口也受权限限制。特殊核心书保持只读，接待期间冻结准备操作，断线角色由房主确认清理后重新认领。

本机检查与尚待验证事项见 [阶段 3 卡组验证](docs/阶段3卡组验证.md)，双人操作见 [给测试玩家的卡组测试说明](docs/给测试玩家的卡组测试说明.txt)。v8 与 v7 协议不兼容，双端需使用同一测试包。本轮仍停留在 F9 准备原型，尚不支持合作接待。

## 阶段 3.1 原版卡组界面（v9 开发测试）

隐藏 F9 后，使用游戏右上“联机准备”认领馆员，点击“编辑角色卡组”进入原版页面。原版左侧馆员列表可切换角色，库存、搜索、筛选与单卡增删使用原版组件。页面显示房主的独立会话模型，操作继续由房主确认；普通原版外观、HP、混乱及有效被动使用有界显示 DTO。

双方先进入自己的图书馆再打开编辑页，进度无须匹配。v9 包中核心书更换、被动继承、清空/预设与特殊卡组尚不可编辑；普通换书和被动分别在后续 3.2A/3.2B 扩展。v9 与 v8 不互通；v8 回退 ZIP 保留。基本原版页面流程已获用户双端确认，库存争抢、断线与存档隔离等专项继续按记录验收。实现边界与验证见 [阶段 3.1 验证记录](docs/阶段3.1原版卡组验证.md)，操作见 [原版卡组双端测试说明](docs/给测试玩家的原版卡组测试说明.txt)。

## 阶段 3.2A 原版核心书页更换（v11 基本流程已确认）

在原版卡组页点击角色核心书页，或右上“查看/更换核心书页”，进入原版核心书库。页面使用房主实例级书库与独立显示模型，只允许为自己认领的馆员选择空闲普通核心书；同名不同实例、其他楼层装备和被动来源占用分别核对。房主执行原版换书并同步实际卡组、库存、属性、有效被动和外观，失败恢复受影响对象，成功后保留馆员认领并撤销旧按钮事件。

v11 同时修复库存标记与房主事务中的空草稿误判，保留真实草稿和占用限制；按钮显示具体只读原因，并防止对已销毁 Unity 控件执行退出恢复。用户已确认双端正常更换核心书页，其他专项继续按清单验收。被动配置编辑、固定/特殊/多卡组、预设及合作接待按后续节点实施。v11 与 v10/v9 不互通，双端使用同一 `RuinaCoop-stage3.2A-v11-core-pages-fix-test.zip`。详见 [全只读修复记录](docs/阶段3.2A核心书页只读修复.md) 和 [核心书页双端测试说明](docs/给测试玩家的核心书页测试说明.txt)。

## 阶段 3.2B 原版被动编辑（v13 容量修复）

点击馆员被动栏或“查看/编辑被动”，在原版继承弹窗选择房主来源书和被动。本地草稿在应用时整组提交，由房主检查来源占用、点数、槽位和互斥规则；取消丢弃草稿。卡组、核心书和被动修改共用资源版本，其他角色保持只读，旧页面和迟到确认不能改动新配置。

v13 将完整被动池无损压缩，修复505本核心书库下因PacketLimit导致双方无法打开页面；同规模完整快照回归为34435字节，原消息上限和权限规则保持有效。v13与v12/v11不互通，双端使用同一新版包。实现记录见 [阶段3.2B](docs/阶段3.2B被动编辑验证.md) 和 [容量修复](docs/阶段3.2B被动书库容量修复.md)，双端步骤见 [被动编辑测试说明](docs/给测试玩家的被动编辑测试说明.txt)。被动替换基本流程已获用户双端确认；争抢、回滚及存档隔离专项仍需独立结果。现继续3.3接待准备。

## 阶段 3.3 原版接待准备（v16 基本流程已确认）

房主从原版邀请界面选择普通接待并发送邀请，双方查看房主解析的敌方、实际挑战楼层和出战名单。房主选择楼层与名单，玩家认领出战馆员后进入原版卡组、核心书与被动页面；返回保留同一次准备。配置变化撤销就绪，旁观玩家无需就绪。敌方未知波次保留原版隐藏规则，客端无需解锁房主关卡。

v14双端反馈客端不跳转和选人缺失；v15修正主线接待筛选后已能共同进入接待，仍有首次连接需重进、退出/换关不同步及人物形象错乱。v16增加认证前有界连接恢复，以实际确认退出结束接待并禁止旧模型复活，客端新接待重建页面，按主客端隔离人物与敌方头像槽位。两端必须使用同一v16包，修复证据见[接待生命周期修复](docs/阶段3.3接待生命周期修复.md)，v15记录保留在[主线接待跳转修复](docs/阶段3.3主线接待跳转修复.md)。

准备页支持使用普通馆员名单的主线接待和泛用邀请；终局、异常/解放、奥利维耶及替换馆员的特殊接待暂不支持。尚未进入准备显示协议的速度、情绪、费用、抗性栏显示“—”。用户已确认v16基本流程；实现和自动检查见[阶段3.3验证](docs/阶段3.3接待准备验证.md)，历史操作见[接待准备测试说明](docs/给测试玩家的接待准备测试说明.txt)。

## 阶段4A 首幕初始化原型（v18 配装预检修复）

两端必须使用同一v18包 `dist/RuinaCoop-stage4A-v18-preflight-fix-test.zip`。首版仅验证关卡3潤事务所第1次接待，房主和一名客人各控制一位馆员，使用基础战斗书页1至5和无有效被动的白名单核心书。房主开始后先冻结配置并等待控制者确认，再执行一次原版初始化，到第一幕玩家输入前暂停。客端显示权威单位、手牌实例、速度骰、光芒和敌方意图的独立视图，不运行客端原版战斗。

本版不开放出牌、开始本幕或胜负结算。提交前可取消回准备；提交后验证完成或失败都需要退出游戏再重新启动，离房不会解除原版场景暂停。完整范围、自动验证和边界见[4A验证记录](docs/阶段4A首幕初始化验证.md)，双端操作见[首幕初始化测试说明](docs/给测试玩家的首幕初始化测试说明.txt)。真实双端首幕验收仍待用户测试，通过后继续4B/4C。

1010v4/v2反馈确认v17实现错误：原版准备页按费用和ID排序敌牌，预检却逐项比较XML原序，正确的六张牌也被拒绝。v18改为保留重复数量的多重集比较，补上直接执行生产校验的回归和具体配装诊断。已有推荐配装可保留，双方更新后重新就绪，再测试首幕。详见[修复记录](docs/阶段4A首幕配装校验修复.md)。
