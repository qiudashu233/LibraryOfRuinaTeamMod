# 阶段 3.2A：核心书页全只读修复

记录日期：2026-10-08。用户双端测试 v10 后反馈：两端均可进入房主核心书库，但为自己认领的馆员也无法更换任何书页。交付 v11 修复后，用户再次双端测试并确认目前已能正常更换核心书页，允许继续既定方案。3.2A 普通核心书页更换基本流程已通过；并发争抢、异常恢复及双端存档哈希等专项仍按测试清单保留，不将本次简要反馈扩展为这些专项的验收。

修复分支为 `codex/core-page-readonly-fix`，从 v10 的 `625aaa9` 建立。修复包为 v11，进度快照格式仍是 v5；两端必须使用同一修复包。

## 原因与证据

房主日志显示快照本地编解码通过，结合用户反馈可确认房间和核心书库页面已经接通；日志没有记录各书页的限制标记，不能仅从日志确定是哪一项让它们只读。随后检查核验过的真实 `Assembly-CSharp.dll` 构造/加载/草稿初始化 IL，找到与症状一致的生产判断错误。

原版 `PassiveModel` 构造器与 `LoadFromSaveData` 只建立已生效的 `originData`，不会建立 `reservedData`。`reservedData == null` 是正常读档状态，临时缓冲在原版被动继承页面调用 `InitReservedData` 时才建立。v10 的 `EquipmentMirror.HasPassiveDraft` 和 `EquipmentTransaction.HasPassiveDraft` 都把该空值判为“未应用草稿”，导致普通书带上 `DraftMismatch`，界面禁用更换，房主事务也会拒绝。

原版 `BookModel` 虽在构造时创建两个保存数据对象，但读档只填充 origin，reserved 仍是默认空对象。因此已提交继承的接收书读档后，origin 中已有来源列表、reserved 列表为空也是正常状态。无条件比较两份列表会把它误当成待撤销继承。

原有事务替身模型默认同时建立 origin/reserved，并把两者设为相同值，未覆盖原版刚载入存档的状态。这解释了为什么 v10 自动检查通过，而正常游戏内核心书均只读。

## 修改边界

- 库存采集与房主事务同时修正：origin 缺失仍拒绝；尚未建立的被动 reserved 表示没有草稿；已有 reserved 才检查是否存在真实未提交差异。
- 书页级 reserved 仅在它是默认空缓冲、且没有任何被动 reserved 时忽略。已有被动草稿或书页 reserved 已非默认空对象时，仍核对来源列表和占用关系。真正的待修改、待删除和异常状态继续拒绝。
- 不调用原版 `InitReservedData`，不重置真实书库或填充草稿来绕过限制。已生效继承保持原样，被动来源书和已装备目标依旧不可取用。
- 原版更换按钮改为显示具体限制原因，例如未认领、其他玩家的馆员、被动来源占用、未应用草稿或原版禁止装备。启用判定与请求权限一致，旧按下事件及等待确认保护继续生效。
- 房主快照日志增加核心书总数、空闲普通书、草稿、被动来源和已装备数量，后续排查可定位实际限制，无需输出存档或整个游戏模型。

同一日志还记录了离房后的界面恢复异常：对已经销毁、但 CLR 引用仍非空的 Unity 组件调用 interactable/TMP/CanvasGroup 属性。恢复前改用 Unity 对象有效性判断；游戏退出时保留托管字段/教程恢复与镜像释放，跳过已销毁页面的原版刷新和属性写入。该问题的游戏内退出路径仍随本轮复测确认。
