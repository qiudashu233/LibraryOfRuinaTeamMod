## 原因与修改

原版敌方XML卡组为 `[1,2,3,1,2,3]`。准备采集调用 `UnitDataModel.GetDeckCardModelAll` → `GetDeckAll` → `BookModel.GetCardListFromCurrentDeck`，后两处均使用 `SortUtil.CardInfoCompByCost` 排序：先费用、再ID。基础牌1/2/3费用为0/1/1，实际到达准备快照及出战Manifest的是 `[1,1,2,2,3,3]`。

v17的 `NativeBattleStateAdapter.ValidateManifest` 用 `SequenceEqual([1,2,3,1,2,3])` 逐项比较，数量和内容完全正确也被误拒。旧测试只检查XML原序，没有把准备页实际排序后的卡组送入这段生产代码。

v18在预检中使用 `OrderBy(id => id).SequenceEqual([1,1,2,2,3,3])`，只排序比较副本，保持重复张数，未改动准备Manifest、编码摘要或真实运行时五区的有序实例引用。缺牌、多牌、1/2/3数量不符或混入4仍拒绝；没有用去重集合放宽范围。

同时细化拒绝原因：指出具体馆员及其名单序号、核心书ID、有效被动、卡组数量或不支持的卡牌ID；敌方身份/核心/卡组和本机原版数据不符也单独说明。客端处理配置Offer时保留该具体原因。原版核心、关卡、卡牌目录返回的LorId必须与请求一致，避免混入错配数据。

房主开始尝试新增 `Battle preflight` 日志，记录关卡/楼层、馆员索引、host/guest分类、书/卡牌/被动ID及敌方卡组；详情最多1600字符，不含Steam身份、房间号、书实例令牌或存档内容。界面统一更正原版中文名“潤事务所第1次接待”。

原生场景加载、唯一启动许可、首幕冻结与离房持久保护均未改动。客端仍不创建原版战斗模型，不开放出牌、开始本幕或胜负结算。提交之后仍须退出游戏再启动。

## 双端复测

详细步骤见[给测试玩家的首幕初始化测试说明](给测试玩家的首幕初始化测试说明.txt)，已加入新版本安装、最短复测流程、新提示对照和失败时保存内容。已有推荐配装无需随机更改。

1. 两端都更新v18并启动游戏，本机安装状态见下方发布记录。不要混用v17。
2. 房主原版邀请进入潤事务所第1次，F9→Role claims确认 `Selected stage: 3`。出战两位，2/3正常。
3. 房主和客人各认领一位；莱尼/锤哥（皮特可替代）核心，无有效被动，每人规避伤害×3、轻微攻击×3、轻微招架×3。
4. 退出编辑回准备，两端重新确认就绪；房主开始一次，等待冻结/配置确认→初始化→双方首幕校验通过。
5. 比较双方四个角色的体力/混乱、光芒、速度骰、卡牌实例及敌方意图；客端独立数据面板、不能操作出牌是本版预期。
6. 无论通过或失败，若已提交并载入首幕，退出游戏后先复制双方Player.log，再重启。出现具体新提示/超时就保存，不必反复点击。
