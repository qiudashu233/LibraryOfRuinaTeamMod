Ruina Coop v17：首幕初始化详细复测说明
2026-10-10，依据1010v4双端日志修订。适用于已经安装的v17，不需要换DLL或重新安装。

先看本次日志结论
你已经两次选到正确的关卡3，客端认证、接待进入和配置快照同步正常。23次开始尝试都在加载前被配置检查拦截，没有进入首幕初始化。
最后换成了关卡5，它有两波敌人，v17首幕原型不支持。本次需要补一次下述完整配置的首幕测试，不必重复各种错误配置的拦截测试。
之前说明把名称写作“尹事务所”，不够准确。本机简中实际显示“潤事务所”；Mod里部分提示仍用旧称，两者在这里指同一事务所。

一、找到准确的那一场接待
1. 双方使用现有同一v17，启动LOR With Mods并载入图书馆，房主建房、客人加入。客人不需要解锁房主关卡。
2. 房主打开游戏原版邀请页面，在早期接待中找到“潤事务所”，展开它，选择第1次接待。
   同一事务所包含多个接待，不要选择后面那场有“潤”“艾莉”的两波战斗，也不要选只有芬恩的那场。
3. 如按邀请用书来辨认：本场使用“耗子之书”。它是邀请书，不是装备给馆员的“莱尼之页”。
4. 房主从原版页面发送邀请，进入挑战准备。客端应自动跟随打开准备页。
5. 临时按F9，点右侧“Role claims”，查看“Selected stage: 3”。看到3才是本次目标；看到4或5应回原版邀请页重选。
   “Host progress”里的Select是计划选关，不能代替原版发送邀请，也不要用它来假装切换实际接待。
6. 游戏中可再核对：只有一波、两名敌人，名字都为“潤事务所9阶收尾人”。确认后按F9隐藏房间面板。
   你上次日志的context1和context2已经满足关卡3，所以不需要寻找另一家事务所。

二、只让两位馆员出战
1. 房主选择一个普通挑战楼层，建议用两位普通助理馆员，先避开特殊固定/多卡组角色。
2. 在原版准备页，用馆员肖像槽上的“出战勾选框/勾号”取消多余角色，只留下两位。
   点肖像本身主要是选中查看人物；改变出战要点勾选框。客端不能替房主改楼层或名单。
3. 看右上联机准备顶部：“准备版本… · 出战 2/3”就是正确的人数示例。
   分母3是关卡最多允许3人，不要求凑满。不要为了把2/3变成3/3再选第三位。
4. 未出战的角色在Mod名单中标“未出战”；后续认领、配装只处理留下的两位。

三、房主和客人分别认领一位
1. 房主在右上联机准备里认领馆员A，客人认领馆员B。
2. 在房主画面，A应显示“我”，B显示已认领；在客人画面，B显示“我”，A显示已认领。
3. 不要由房主把两人都认领，也不要只在原版肖像上选中人物而漏了Mod的“认领”。
4. 如果改过楼层或出战名单，重新检查归属；这些变化可能撤销原认领和就绪。

四、配核心书和被动（直接使用这套示例）
1. 房主为A点“编辑角色卡组”→“查看/更换核心书页”，换成房主库存中的“莱尼之页”。
2. 客人为B从同样入口换成“锤哥之页”；没有空闲锤哥之页时，“皮特之页”也支持。
3. 使用可装备的空闲实例；已被其他角色装备或作为被动来源的实例仍按原有规则只读。
4. 两位都不要继承被动。若所选实例已附加归属被动，打开“查看/编辑被动”移除继承并应用，不能只关闭尚未应用的草稿。
5. 这三种鼠核心没有原生被动。普通换书成功不等于满足4A：更高级的普通核心及带有效被动的书页本次仍不支持。
6. 推荐先换核心书，再重新整理卡组；换书后自动保留或带来的原卡组不一定符合本轮范围。

五、两位馆员都配成同一套九张基础牌
每位完整卡组如下，两人各一套：
  规避伤害 ×3   （战斗书页ID 1，0费）
  轻微攻击 ×3   （战斗书页ID 2，1费）
  轻微招架 ×3   （战斗书页ID 3，1费）
合计9张，不要少牌，也不要保留鼠核心原来的其他战斗书页。

1. 在原版卡组编辑页逐张移除旧牌，再添加上面三种各3张。当前不依赖清空、预设或自动配装入口。
2. 这些基础牌在原版不扣库存，每种每个卡组最多3张，房主和客人可以同时使用同一套，不需要另外刷牌。
3. 想核对ID时，按F9→“Deck editor”，选择自己的馆员：
   “Deck cards: 9/9”下面应只有规避伤害(#1)、轻微攻击(#2)、轻微招架(#3)，各出现3次。
   名称搜索框可按完整名称查找，Add/Remove是单卡操作，等待房主确认后再继续。
4. 按F9隐藏面板，用“返回准备”退出编辑。两边都结束核心书/被动/卡组编辑，等待“等待房主确认…”消失。
5. 其他可用基础牌为攻守兼顾(#4)、集中攻击(#5)，但这次先按上述固定3+3+3示例，减少不确定因素。
   “原版牌”“普通牌”“白色牌”不等于本轮支持；任何ID大于5的牌都先移除。

六、最后确认就绪，再由房主开始一次
1. 两端回准备页，确认仍是关卡3、出战两位、各归属一人、两位的核心/被动/九张卡组符合上文。
2. 房主和客人分别点“确认就绪”，各自看到“已就绪 · 配置变化后需要重新确认”。
   若一边显示“当前为旁观玩家，无需就绪”，先回第三节检查是否认领了自己的出战馆员。
3. 就绪后不要再换书、加减牌、改名单、改楼层或释放/认领，否则双方需要重新就绪。
4. 房主点击一次“开始首幕初始化验证（结束需重启）”，然后等待提示变化，无需反复点击或退房重进。
5. 正常顺序为：配置已冻结/等待控制者确认→房主初始化首幕→首幕暂停/等待校验→双方首幕状态校验通过。
   配置和首幕确认各有60秒期限。出现明确失败提示就停止重复点击，保存当前提示和双方日志。

七、这次真正要验收什么
1. 房主执行一次原版初始化，停在第一幕玩家输入前；双方出现“联机首幕·初始化验证”数据面板。
2. 客端本版显示独立权威数据面板，底下可能仍是准备场景，不会加载一套客端原版战斗。这属于v17实现范围。
3. 两边都显示“首幕状态校验通过”，体力/混乱、光芒、速度骰、手牌/牌库和敌方意图一致。
   同名牌仍有不同#实例号；敌方已选牌可同时出现在已用区和保留区，此时应是同一实例号。
4. 双方不能出牌、撤牌、自动配牌、开始本幕或胜负结算。本次只验证初始化，不能继续打一幕。
5. 验证结束后退出游戏，先复制保存双方Player.log，再重新启动。提交后的房主场景不能靠退房恢复。
   本次旧日志没有进入提交阶段，因此它们尚未验证这一暂停/重启边界。

八、提示对照与反馈
“所有实际控制者必须确认当前配置就绪”：两端都退出编辑，检查自己的归属，再分别重新就绪。
“4A requires ordinary supported key pages”：某位出战馆员处于固定、多卡组或显示不支持状态，先用普通助理及上述鼠核心。
“4A requires exactly two librarians…”：这是配置清单的总体校验失败，不只检查人数；人数为2/3时还应检查是否恰好房主/客人各控制一位。
“4A仅支持…基础战斗书页1至5…”：综合白名单检查未过。按第四、五节检查两位完整配装，不要只看当前选中的一位。
“4A requires a fresh single-wave reception”：检查Selected stage，关卡5有两波，请选回关卡3；本次不是要求先去通关解锁。

若按固定示例仍被拦截，先停止改配置，反馈以下内容：
  - F9→Role claims显示的Selected stage数字；
  - 实际出战人数与两位馆员分别归谁控制；
  - 两位核心书名称、有无继承被动、完整九张卡组；
  - 两边是否都显示已就绪、点击后完整提示；
  - 房主和客人的Player.log，重启前先保存。
日志默认位置：%USERPROFILE%/AppData/LocalLow/Project Moon/LibraryOfRuina/Player.log。
现有v17部分提示只给综合原因，没有记录具体哪一位/哪张牌，不能仅凭它猜测配置。若固定示例仍失败，再针对真实失败点修复，不需要继续随机换关或反复点击。
