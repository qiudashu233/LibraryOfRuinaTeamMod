记录日期：2026-10-09。用户已确认 v13 双端正常替换被动，本节点从 `805396c` 接续；开发分支 `codex/reception-preparation`，房间协议14，快照8。基本功能确认不替代库存争抢、异常回滚及双端存档隔离专项。

## 本次实现

房主从原版邀请页面选择普通接待并发送邀请，沿用房主原版要求检查及准备初始化。双方进入同一次挑战准备，查看房主实际解析的敌方、可挑战楼层和出战名单。客人的关卡进度无需匹配；客端不执行 `PrepareBattle`、接待初始化或邀请任务，而以独立显示模型复用原版界面。

房主选择实际挑战楼层与出战馆员，受该接待人数上限、楼层可用状态、死亡和锁定限制。采集遍历 `GetUnitBattleDataList()` 与 `IsAddedBattle`，不调用会自动补选的 `GetUnitAddedBattleDataList()`；新准备的默认名单由房主转换明确初始化。未认领的出战馆员由房主控制，认领者为该馆员的控制者。非出战馆员不能认领和修改；其他人的角色可以只读查看。

玩家在右上联机准备区认领馆员，进入已验收的原版卡组、核心书和被动页面，返回时保留关卡、楼层、名单及敌方预览。退出查看后可点击“查看挑战准备”重新进入。每次新接待拥有独立 ContextId，即使重新选择同关卡也撤销旧认领与按钮事件。

总准备版本包含接待上下文、敌方显示、楼层、名单、认领、卡组/核心书/被动资源版本与控制者连接情况。上述配置变化撤销就绪；就绪操作本身不增加准备版本。只要求实际控制者就绪，旁观玩家无需就绪。就绪请求经已鉴权的 Relay、房间校验、请求去重及当前版本裁定，客端收到对应权威状态后结束等待。准备状态只在快照编码与本地验证成功后提交。

原版预览存在重新随机敌方核心书的路径，因此双方敌方展示统一使用房主 StageModel 已解析的数据。未清关或低章节下的后续波次采用原版整行问号占位，避免泄露未显示的单位及人数。

## 明确边界

- 本包交付普通接待准备；终盘、特殊替换馆员、超出 DTO 或页面容量的接待明确显示不支持。
- 同步敌方 HP、混乱、有效被动、核心书、卡组及可用外观。速度、情绪、费用、抗性等尚未进入显示协议的动态栏显示“—”，不代表已完成战斗初始化。
- 房间内双方的 `OnClickBattleStart`、`OnClickGameStart` 和 `LoadBattleScene` 均拦截；全部就绪也暂不能开战。后续按原方案实施 4A 初始化及 4B/4C 单幕同步后再开放。
- 房主原版准备包含成就、任务及真实模型操作；客端显示不沿用这些入口。普通邀请准备只记录使用书，原版失败结算才扣书，本节点没有添加开始时扣书。
- 本机自动检查不启动 Unity、不调用真实接待/继承/保存操作。新增页面运行、双端同步和客端存档隔离仍需实际测试。

## 双端验收

1. 两端使用同一 v14 包，均从“继续游戏”进入各自图书馆，再 F9 建房/加入，随后隐藏 F9。
2. 房主从原版邀请界面选一个普通、已可邀请的关卡并发送邀请。客机应自动显示同关卡挑战准备，无需自己的存档解锁。核对当前波敌方、书页、卡组及问号；未清关后续波次不应暴露隐藏信息。
3. 房主切换可挑战楼层和出战馆员，核对双方名单、人数上限及勾选状态。非出战者不能认领；两人分别认领出战者，其他馆员保持只读。未认领出战角色由房主控制。
4. 各自编辑卡组、普通核心书和被动，返回后应仍是同一次准备，不重复初始化、随机敌人或进入战斗。核对共享库存与双方显示。
5. 各控制者确认就绪。任一配置变化后就绪均撤销；旁观者无需就绪。移出名单清理对应认领，新接待清空旧认领；断线后对应控制者不再就绪。
6. 编辑期间房主更换接待或楼层，旧页/旧草稿应退出或失效，迟到输入不能修改新馆员。客人关闭预览再“查看挑战准备”应恢复当前上下文。
7. 点击开始应仍被阻止。退出房间后原版单机操作恢复；客端不会因此获得关卡解锁或奖励。记录测前测后客端存档哈希，并保存双方 Player.log，报告所选关卡、楼层及失败步骤。
