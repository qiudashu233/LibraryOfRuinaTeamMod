# 阶段 3.2B：被动书库容量修复（v13）

记录日期：2026-10-09。用户双端测试 v12 后反馈：双方已认领各自馆员，点击“查看/编辑被动”仍提示房主被动不可用。修复分支 `codex/passive-pool-fix` 从 v12 提交 `875f2dc` 接续。

## 根因与日志证据

房主 `Player.log` 反复记录 `passive inventory unavailable: PacketLimit`；当时核心书实例为 505、本已有被动来源为 77、装备为 57、未提交草稿为 0。选关后的基础快照约 30,815 字节，已占消息上限 65,536 字节的一部分。

v12 将完整被动池直接写入同一个进度包。每个普通原生槽约占 12 字节，空槽也发送；真实游戏 `BookXmlInfo` 默认继承槽数量为 9。505 本书的槽与来源关系叠加基础快照后会超限，采集器于是清空整个被动池并标记 `PacketLimit`，保留卡组/核心书数据。原版弹窗要求完整被动池，因此房主和客人都会在打开之前被拒绝，角色认领成功也无法解除这个限制。

日志未记录每本书的实际槽分布。本轮没有读取存档全文或调用真实存档模型；回归用例按已观察到的书库规模和真实默认槽数构造完整数据，复现原始编码超限。

## 修复

- 被动池传输改为无损 Deflate 编码，保留每个实例、原生/当前槽位、零借用来源和已提交继承关系；容量预算使用实际压缩后的线格式，不截断列表。
- 消息总量上限保持 65,536 字节，展开数据上限为 4 MiB，足以容纳当前有界 DTO 的最坏形状。读取前检查声明长度，严格拒绝短流、缺失结束标记、尾随数据、额外压缩流与展开超限，解码和关系验证仍在发布前完成。
- 装备修订号比较继续使用未压缩的规范化内容，避免不同运行时压缩输出影响状态版本。角色权限、来源竞争、事务回滚及 ACK/快照屏障沿用已有实现。
- 页面区分传输容量、采集失败、核心书库不可用、目标结构不支持、等待同步和待确认状态；日志记录具体失败原因及书库数量。
- 房间协议升为 v13、快照格式升为 v7，两端须安装同一包。
