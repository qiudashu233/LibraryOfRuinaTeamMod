## 已确认的筛选错误及选人连锁

v14 的 `NativePreparation.Capture` 通过 `StageClassInfo.IsNormalInvitation()` 判定是否支持普通接待。实际游戏 IL 显示，这个方法返回 `invitationInfo.combine == BookValue` 或 `isStageFixedNormal`，用于泛用邀请分类，并不表示“所有使用普通邀请入口的接待”。普通主线的固定书籍邀请也会走 `ConfirmSendInvitation → UIController.PrepareBattle → StageController.InitStageByInvitation`。

因此，v14 会把不满足泛用邀请标志的普通主线接待直接标为 `UnsupportedStage`。这是正常分支提前返回，不抛异常，所以旧日志不会出现 `Native preparation capture` 错误。其后有两条连锁路径：

1. `NativePreparation.Tick` 看到准备状态不可用，不创建客端挑战准备镜像，客端无法自动跳转。
2. `PrepClaims.ReconcilePreparation` 在准备不可用时清空所选楼层和认领上下文；原版配装区域要求存在有效楼层与馆员卡组，所以原有选人/认领入口同时消失。

客端收到更多进度快照也不能修复这个问题：房主每次仍生成相同的不可用准备状态。

开战守卫不是普通主线进入准备页的前置阻断。实际 IL 中，准备页经 `OpenBattlePrepare → StartBg(0)` 打开；`OnClickGameStart` 经 `OnClickBattleStart` 调用并启动战斗切换。此次修复继续保留开战保护，不能通过放开单机战斗来绕过准备故障。

## v15 修复范围

支持范围判断改为独立的 `IsSupportedInvitation`，不再依赖泛用邀请标志。原版普通主线及泛用邀请均可继续准备；仍要求基础游戏正整数 ID、`StageType.Invitation`、非终盘入口，并保留当前楼层实际馆员引用、人数限制、DTO 容量及敌方数据校验。

特殊接待按实际游戏的 `EndContentsStageId` 枚举排除，包括 `70001..70010`、`610000`、`60003`、`60004`、`60007` 及 `210005..210009`；同时排除 `SpecialStageIds.olivier`（`60002`），其未通关准备存在替换 Roland 的原版分支。`StageType.Creature` 的异常战与完全解放不在本次支持范围。其他只涉及特殊敌方机制、仍使用正常馆员名单的主线，不因存在于 `SpecialStageIds` 就一律拒绝。

新增快照诊断记录准备阶段、可用/拒绝原因、ContextId、关卡、楼层以及实际出战人数和上限；启动日志增加协议版本。后续能够区分“没有准备上下文”“明确不支持”“捕获失败”和“已收到可用准备”。双端应使用同一 v15 包。

### 首次默认出战名单

独立检查发现，原版 `StageLibraryFloorModel.Init` 会调用 `GetUnitAddedBattleDataList()`；该 getter 在空选时自动选中第一位馆员。v14 的 `InitializeDefaultRoster` 只要发现任意已选馆员就返回，而准备补丁又屏蔽原版 `SetToggles` 的首 N 人默认选择，导致首次默认出战常只剩一人。

v15 在每次新接待、每个楼层首次初始化时，按该接待人数上限选择前 N 位可用馆员，跳过死亡、锁定和不可用人物。随后刷新页面、切回已初始化楼层或从卡组/核心书/被动编辑返回时，保留房主已经调整的名单。这是静态检查确认的独立缺陷；旧日志没有出战人数字段，不能写成用户本次已直接观察到的名单数量。

### 敌方区域透明度

同时修复一个潜在连带问题：原版邀请阶段会调用敌方列表 `Activate(false)`，将其 `CanvasGroup` 的 `alpha`、`interactable`、`blocksRaycasts` 关闭；原版挑战准备通常由 `OnUpdatePhase` 恢复。联机镜像为避免使用客端本地敌方模型而接管了该回调，因此独立渲染现在显式恢复这三个显示/交互属性，并在退出镜像时恢复原值。客端普通准备布局、楼层按钮区域和普通边框也显式恢复，隐藏仍指向客端存档的本地馆员楼层按钮；这些变化均通过现有恢复记录保存并还原。

这一点由实际原版 IL 与镜像路径比较得出，日志并未证明用户此次已经到达有效镜像后再被透明度隐藏。它属于修复跳转入口后需一并排除的展示隐患。

## 自动检查及原覆盖缺口

v14 已通过协议、状态、事务、补丁目标签名及只读 IL 检查，但这些检查没有实际执行游戏内主线邀请条件，也没有两个 Steam 账号驱动 Unity 页面。因而“目标方法存在、桥接结构正确”未覆盖“主线邀请标志为 false 时仍应允许准备”的语义错误；默认出战 getter 的补选行为及敌方面板原有透明度也需要独立断言。

v15 已补充并运行以下针对性检查：

- 在实际编译程序集上验证普通主线 `BookSpecial` / `BookRecipe` 与泛用 `BookValue` 均允许；不能仅再次检查辅助方法名称存在。
- 验证终盘枚举、异常战、替换馆员接待及非原版 ID 仍拒绝，并继续执行名单引用和容量校验。
- 验证首次默认名单按上限填充、跳过不可用人物，后续刷新保持用户选择。
- 验证敌方列表自身 `CanvasGroup` 的显示、输入及恢复路径。
- 回归准备状态/快照、认领与撤权、卡组/核心书/被动、就绪确认及开战保护。

## 双端复测步骤

1. 两端关闭游戏并使用同一个 v15 包，以带 Mod 模式进入各自图书馆，再由房主建房、客端加入。核对启动日志协议版本一致。
2. 房主从原版邀请界面选择一个已解锁的常规主线，发送并确认邀请；先用已经通关、无需前置剧情的接待。客端应自动进入同一次挑战准备，右上联机区域应出现楼层、出战馆员及认领入口。
3. 核对双方关卡、敌人、当前波次和默认出战名单。人数大于一的接待应默认选满可用人数；锁定人物不能被自动选中。房主增减出战人物后双方勾选一致，非出战人物不可认领。
4. 双方分别认领不同的出战馆员，编辑卡组、普通核心书和被动并返回。关卡、楼层、名单与敌方应保持一致；各自只能修改有权限的人物。
5. 切换可用楼层后再切回，确认已编辑的名单没有被重置。客端退出查看后重新打开挑战准备，敌方列表应可见且能选择查看；关闭房间后原版界面恢复。
6. 再测试一个泛用邀请，以及一个有前置剧情的未通关普通主线。剧情路径需记录房主完成或跳过剧情后的页面和同步结果；后续波次继续按房主可见性显示问号。
7. 检查就绪撤销、换接待清理认领和旧页面失效。点击开始仍应被阶段 4 门槛阻止，不应直接进入单机战斗。
8. 若失败，在重新启动游戏前保留双方新的 `Player.log`，记录所选关卡名称/ID、楼层、操作顺序与页面现象。对照两端新增准备诊断字段，可判断状态未采集、支持范围拒绝、捕获失败或镜像显示问题。

阶段 3.3 双端复测通过后，继续既定阶段 4A 战斗初始化；本轮修复不代表合作战斗已完成。
